ARCHITECTURAL NOTE — LocalSystem Service (NOT a finding)
---------------------------------------------------------
The endpoint service running as LocalSystem is BY DESIGN and correct.
The entire premise of Raizen is that SYSTEM is the broker: instead of
elevating a user account, the service executes specific approved actions
on behalf of the user under its own identity. The compensating controls are:

  - Server-side approval before any action is executed
  - Action type whitelist (no shell — dedicated C# handlers only)
  - Parameter schema validation per action
  - HMAC-SHA256 audit chain detecting tampering
  - Append-only audit table enforced at DB permission level

This is the correct architecture for a JIT elevation platform. It should
be documented as an accepted architectural decision, not a risk item.

DevAdmin Scheme (RECLASSIFIED — Low / Informational)
---------------------------------------------------------
The DevAdmin auth scheme is properly double-gated:
  (1) ASPNETCORE_ENVIRONMENT must equal "Development"
  (2) DevMode:Enabled must be explicitly true in config
Both must be true simultaneously. This is acceptable. A startup assertion
was added as belt-and-suspenders (see Phase 1, Item 1 — DONE).

       • Standalone full-page TOTP enrolment (no layout, visual match to Login)
       • 3-step flow: install app → scan QR code → enter 6-digit code

       • "Skip for now (X days remaining)" link visible only during grace period

   - Password minimum raised from 8 to 12 characters for new users in Settings
   - DB migration included in Web Program.cs startup (ALTER TABLE IF NOT EXISTS)
   - DbSetup.cs updated for fresh installs

   NOTE FOR EXISTING INSTALLS: Existing admin accounts retain RequiresMfa=false
   until an admin manually toggles it per-user via the Settings page. This is
   intentional to avoid locking out existing operators on upgrade day.

   ISO 27001: A.10.1.2
   Severity: High

   Current: PollSigningPrivateKeyPem stored in appsettings.Production.json

   Fix: ConfigWriter writes DPAPI-protected binary (ProtectedData.Protect,
   LocalMachine scope) to poll-signing.key.dpapi in ProgramData\Raizen.
   API Program.cs loads and unprotects it at startup. Key removed from

   first startup after upgrade, auto-migrate to DPAPI and delete the key.
   Files: ConfigWriter.cs, WizardState.cs, API Program.cs


⏳ ITEM 9 — Password storage migration: pure PBKDF2-SHA512 (V2 scheme)
   ISO 27001: A.10.1 / NIST SP 800-63B
   Severity: High

   Current: AES-256-GCM wraps PBKDF2-SHA512 output. Reversible if
   EncryptionKey is known. Password storage should be one-way only.
   Fix: Add V2 scheme — pure PBKDF2-SHA512, 150,000 iterations.
   On login with V1 hash: verify with old logic, immediately re-hash V2.
   New password sets always use V2. No forced resets on upgrade day.
   After 6 months, warn if V1 hashes remain. After 12 months, force reset.
   Files: AdminAuthService.cs
